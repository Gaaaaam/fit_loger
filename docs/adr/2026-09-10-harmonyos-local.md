# ADR：HarmonyOS 原生 + 本地 SQLite

- 日期：2026-09-10
- 状态：已采纳
- 范围：当前产品，不含上架运营

## 决策

1. **只做 HarmonyOS NEXT 原生（ArkTS / ArkUI），当前不做 iOS / Android。**
2. **数据存在本机 `relationalStore`（SQLite），不用 Firebase / Supabase 等 BaaS。**
3. **3D 肌群点选使用 `@kit.ArkGraphics3D`，作为选动作的一条路径，失败时必须能退回列表。**

## 为何不是 Flutter / 跨平台

本应用的目标设备是华为手机。HarmonyOS NEXT 与 Flutter 的系统 API（关系型库、ArkGraphics3D、主题、文件导出）不能靠一套 Dart 代码吃到同等能力。跨平台省的是「第二套商店」，而当前明确不做 iOS/Android，省下来的工期应放在录入和数据安全，而不是抽象层。

以后若要上其他系统，应视为新平台移植，而不是「本来就该一套代码」。

## 为何不是 BaaS

健身房经常没信号。录入必须在断网时可用。账号和同步会引入登录失败、冲突合并、隐私合规，收益与当前用户规模不匹配。换机用 JSON 导入导出即可验证「数据能带走」。

云同步列为冰柜，直到真有第二台设备或第二位用户证明本地导出不够。

## 3D 的维护成本

人体 glb、手势、射线拾取、深浅色清屏是独立技术岛：生态样本少、真机 GPU 差异大、AI 生成代码不准。约束：

- 模型加载失败必须有重试和肌群列表退路。
- 业务规则（推荐动作、多选）留在纯函数里，不写进 Scene。
- 不为 3D 再加骨骼动画、服装、体型扫描。

`Camera.raycast` 的 `hitPosition` 是包围盒入口，不是三角面。`base_skeleton` 和 `base_connective` 的盒子比可见肌肉更靠外；若「最近命中不是肌群就放弃」，正面和侧面几乎点不中。`nearestSceneMuscle` 因此忽略这两块，只让 `base_head` 挡住更远的肌群。

肩、胸、手臂的盒子会互相伸出几厘米。在最近肌群入口的 0.12 单位内，选射线离包围盒中心最近的那一块：点肩部中间是三角肌，点胸口仍是胸。手掌和脚面没有单独遮挡壳，射线可能落到邻近的前臂或小腿。节点没有位移时，网格局部包围盒中心就是世界坐标。规则由 `node tools/verify_scene.mjs` 锁住。

## 后果

- 应用市场路径是华为，不是 App Store / Google Play。
- 无多设备实时同步。
- ArkTS 校验用 Node 镜像/抽类型脚本，没有 Flutter 那样的设备无关 widget 测试生态。
